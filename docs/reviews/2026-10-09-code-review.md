### Cross-cutting
- **No market gate on US coverage copy.** Setup enables stolen/damaged/undelivered coverage and writes that copy for any store (app/merchant/configuration.server.js:31, extensions/insurance-ext/locales/en.default.json:3, Checkout.jsx:360), with no shop-country check. An Australian store can install a Public app, so it would sell protection that overlaps Australian Consumer Law remedies, which AGENTS.md forbids. Raised by §1, §2 and §6. **Migration 20261008000000_us_coverage_flags turns lost and damaged coverage back on for every CHECKOUT_UI_CART_TRANSFORM shop.** That undoes 20261006010000_disable_consumer_law_coverage for any existing (for example AU pilot) store, and also overrides merchants who had switched those flags off on purpose.

### 1. Extensions (unverified)
1. **Checkout.jsx:229. The block can get stuck after a cart write succeeds.** `awaitingCart` clears only once the expected change appears in `shopify.lines`, and nothing times it out. If the change never shows up (for example, Shopify normalises a `_yasas_protection_*` attribute), every later action is skipped, including removal. `mutationFailed` stays false, so no Retry button appears.
2. **shipping-protection.js:318. A protection line on a replaced variant is orphaned.** A line counts only if it uses the currently configured variant. If setup repair moves to variant B mid-session, the old line on A stays at the $0 fallback price, the block can't remove it, and it offers protection again, so the buyer can end up with two lines.
3. **Checkout.jsx:82. The quote can stay pending for the whole session.** When the cart has an order-level discount, the quote needs `localization.country` and Storefront visibility for every eligible variant. If either is missing, the quote stays 'pending'. An existing protection line then reads "unavailable", and nothing retries after 3 attempts.
4. **cart_transform_run.js:19. The fee logic is copied three times.** The currency minor-unit tables, BigInt fee rounding and contract validation exist in app/pricing-contract.js, the Function and the checkout block, so they can drift apart. A shared pure module would need to avoid BigInt `**`, because the block bundles to es6.
5. **shipping-protection.js:113. The block's config parser doesn't normalise its output.** `validateConfiguration` returns the raw object, while the server and the Function normalise theirs. A stray `ruleId` on a v1 config leaks into attributes and into `reconciliationKey`.
6. **Checkout.jsx:189. Perf: JSON work on every render.** `reconciliationKey` stringifies the whole config and every cart line on each render, and `priceRequest` is stringified and then parsed again.

Checked and fine: BigInt `**` in the Function (the CLI keeps es2022); function-failure, subscription and pickup behaviour (matches docs/agents/protection.md).

### 2. Pricing & protection (unverified)
1. **shipping-protection.server.js:307. runSetup can roll a live store back to an old rate.** It republishes the DB's active rule (v2) as soon as product and variant match, without reconciling a newer rule (v3) that is already live in Shopify. That happens after a metafieldsSet that timed out but landed (v3 FAILED or PENDING). The fallback at line 325 also prefers `activeRule.rateBasisPoints` over the live contract.
2. **pricing-rule.server.js:158. The publish-failure cleanup marks the rule FAILED without a `state: PENDING` guard.** If a concurrent settings-loader reconcile has already activated the rule, the shop ends up pointing at a FAILED active rule.
3. **protection-admin.server.js:559. Setup that fails partway can orphan duplicate products.** If setup fails after createProduct but before the product ID is saved (for example, when the merchant's own `shipping-protection` handle forced the suffix -1), the retry can't find the product and creates another one.
4. **shipping-protection.server.js:266. Setup can delete the active rule's variant.** With the shop metafield missing, the product is found through `activeRule.productId`, but the rule's variant isn't the one kept, so repairProduct may keep another variant (`variants.nodes[0]`) and bulk-delete the rule's variant V.
5. **protection-admin.server.js:230. buildChecks blames the variant when the metafield is missing.** It looks up the variant from `shopConfig` only, while `source` and publishRate fall back to transformConfig. With a missing shop metafield, health reporting flags the variant instead.
6. **shipping-protection.server.js:47. The dashboard misstates the live price for legacy seeds.** pricingRuleCheck skips the rate comparison for a legacy schemaVersion 1 seed, so it can show the DB rule's 1% while checkout charges 0.25%.
7. **checkout-offer.server.js:43. Duplicated checks.** The session-shop and installed-generation checks are re-implemented here, and the generation check is copied three times in pricing-rule.server.js (40-47, 134-139, 189-195). `assertSessionShop` and `ensureInstalledShop(..., expectedGeneration)` already exist.
8. **shipping-protection.server.js:88. Perf: repeated and sequential reads.** `ensureInstalledShop`, `getShopConfiguration` and `loadCore` are called repeatedly per request, and independent reads are awaited one after another. A rate save runs about 3 loadCore GraphQL calls.
9. **protection-refunds.js:32. Dead code.** The `unknownLine` branch is unreachable, and the `shopDomain ?? core.shop.myshopifyDomain` fallbacks (shipping-protection.server.js:68, 231) are never used.

### 4. Shop, auth & sessions (unverified; recorded before §3, which was still running)
Marked **[PR #24]**: addressed by PR #24 (the PR #21 code-review follow-up, merged 2026-10-09), going by its commit message and not re-checked against these findings.
1. **[PR #24] session-storage.server.js:74. storeSession can lose a refreshed offline token.** It calls Shopify (verifyInstallation) before saving, so a transient failure (timeout, 5xx, throttle, lost lease) throws away the freshly refreshed token pair. If refresh tokens are single-use (not checked), the worker loses Admin access until the merchant reopens the app.
2. **shop.server.js:86. redactShopData can wipe a live installation.** It deletes the Shop row and all its data without checking that the shop is still UNINSTALLED. A shop/redact delivery retried after a reinstall would destroy the reinstalled shop's data. Check whether Shopify sends shop/redact after a reinstall.
3. **shop.server.js:63. A replayed uninstall can uninstall a reinstalled shop.** markShopUninstalled doesn't compare the webhook's trigger time with the current installation, so a delayed or retried app/uninstalled flips a reinstalled shop to UNINSTALLED and deletes its new sessions.
4. **[PR #24] shop.server.js:50. A concurrent uninstall returns a 500 instead of the re-auth 401.** ensureInstalledShop's `shop.update` with a generation in the where clause throws Prisma P2025, not InstallationAccessLostError.
5. **session-storage.server.js:100. A domain change can block installation for good.** `shopGid` is @unique and nothing handles an older Shop row that already holds the GID (for example after the myshopify domain changes), so OAuth hits P2002 every time.
6. **[PR #24] admin-graphql.server.js:111. A lost settings lease shows a generic error.** If the lease is lost during a throttle or pacing wait, `timers/promises` rejects with a generic AbortError. The merchant gets a generic error instead of the lease's UserFacingError, and the abort is logged as `shopify_graphql_failed`.
7. **admin-graphql.server.js:74. Per-shop pacing fails under parallel load.** (PR #24 caps the per-shop throttle wait. Check whether that also fixes the thundering herd.) waitForShop releases every waiter at the same deadline, so they send all at once, drain the bucket again, and fail together after 3 retries.
8. **[PR #24] session-storage.server.js:114. Perf: a full table count while holding a lock.** Each storeSession builds a new PrismaSessionStorage, whose constructor runs `pollForTable()` (a COUNT(*) on Session) while the Shop row lock is held. If the count fails, it sleeps 5s while still holding the lock.
9. **session-storage.server.js:124. Perf: three queries per authenticated request.** loadSession runs session, shop and session again, one after another, on every request and webhook. One `findUnique` with `include: { shopRecord: true }` would do it.
10. **session-storage.server.js:20. Duplicated transport.** verifyInstallation hand-builds an Admin GraphQL fetch transport that duplicates loadAdminGraphql. The 401 → InstallationAccessLostError mapping exists only in this copy.

### 3. Orders & webhooks (unverified; no subagents were used and the reviewer flagged 1 and 6 as uncertain)
1. **order-ingestion.server.js:286. A refund that becomes IGNORED leaves a stale row.** The refund is skipped with `continue`, so an earlier PENDING row is never updated or removed and its updatedAt never moves. It stays at the head of the recheck queue (order-reconciliation.server.js:226-235) forever, and 20 or more such rows starve real rechecks. Uncertain whether PENDING → IGNORED can actually happen.
2. **order-ingestion.server.js:116. The single same-second refresh can be used up, letting a stale copy win.** A content change without an updatedAt bump uses the one refresh allowed per version. A later stale copy at the same updatedAt passes (equal timestamps aren't rejected), overwrites newer data, and can't queue another refresh. The root fix is to order writes by fetch time.
3. **order-reconciliation.server.js:187. Serialization conflicts are counted as an outage.** Leftover P2034 conflicts count toward MAX_CONSECUTIVE_ORDER_FAILURES, so contention during a webhook burst aborts the turn, raises `reconciliation_failed`, and backs the shop off for 5 minutes.
4. **order-reconciliation.server.js:156. One turn can run for minutes.** The time budget is checked only between pages. A 250-order backfill page of full fetches takes minutes against a 60s budget, which blocks other shops, the retention purge and SIGTERM. Check per order and keep the cursor.
5. **order-reconciliation.server.js:240. Unfetchable orders' pending refunds are rechecked and alerted forever.** Pending refunds whose order is gone or older than 60 days are rechecked every 10 minutes and raise `refund_recheck_failed` each time. Treat OrderUnavailableError as terminal, as the worker does.
6. **order-normalization.js:114. The recorded fee may include order-level discounts.** `discountedTotalSet` may exclude order-level discount allocations (unconfirmed), which would overstate the recorded fee and covered merchandise. Check `discountAllocations` or `discountedUnitPriceAfterAllDiscountsSet`.
7. **order-ingestion.server.js:222. Order edits trigger false price alerts.** livePriceCheck includes lines added by an order edit before first payment, which raises false UNMATCHED / `protection_price_unmatched` alerts.
8. **order-shopify.server.js:85. Some permanent failures are retried as temporary.** Hitting the page limit and "data is incomplete" throw plain Errors, so they're retried 16 times over about 6.4 hours with alerts. They should throw PermanentOrderError.
9. **order-ingestion.server.js:175. Perf: unchanged orders are rewritten in full.** Every persist rewrites all lines and refunds even when the hash is unchanged, which means more writes and more serialization conflicts. The refund-recheck rotation currently depends on that rewrite.
10. **order-ingestion.server.js:203. Cleanup.** `(!existing?.firstPaidAt || firstPayment)` is redundant, and the eligible-line filter is repeated 3 times (125, 217, 222).

### 5. Admin UI & analytics (unverified)
1. **app.jsx:31. Any unexpected loader error blanks the dashboard.** `boundary.error` rethrows non-Shopify errors and root.jsx has no ErrorBoundary, so a single GraphQL throttle or timeout in readShippingProtectionState or readOverview shows the default "Unexpected Server Error" page inside the Admin iframe.
2. **app.settings.jsx:104. "Settings weren't saved" can be wrong.** update-rate, setup and enable show it for any non-UserFacingError, even though they publish to Shopify first and the change may already be live. disable and update-copy already use "couldn't confirm, refresh" wording.
3. **analytics.server.js:48. Unresolved refunds drop out of the review notice.** PENDING and UNATTRIBUTED refunds are loaded only if they were created within about 31 days, so old unresolved refunds disappear from "Some records need review". aggregateAnalytics (analytics.js:98) also counts edge-of-window refunds without an exact-range check.
4. **app.overview.jsx:214. Overview overstates readiness.** It says "Customers are offered protection" when `protectionEnabled` is true, but that doesn't confirm the checkout block is placed. This contradicts docs/agents/admin-ui.md, and Settings already says "Add its block to checkout".
5. **app.overview.jsx:13. Perf: Overview runs a full state read for 3 fields.** Every load and Refresh runs readShippingProtectionState (loadCore, product lookup, ensureInstalledShop twice, a possible reconcile write from a GET) just to read enabled, off and rate.
6. **analytics.server.js:37. Perf: every order in the window is loaded into memory.** All orders and refunds from about 32 days are aggregated in JS on each request, including unprotected ones. SQL aggregates or a protected-only query would scale better.
7. **analytics.server.js:59. Normal paging looks like an initial backfill.** `sync.complete` is false whenever the reconciliation cursor is set, including normal multi-page incremental windows, so busy stores see "still syncing, numbers may be incomplete".
8. **entry.server.jsx:52. Streaming render errors are missed.** They go only to console.error, not reportFailure, and setting `responseStatusCode = 500` after the shell resolves does nothing.
9. **analytics.js:23. Dead analytics surface.** readAnalytics, the custom and all-time presets, and many fields are computed and sent to the client but never shown. `readAnalytics({search: 'range=7'})` throws because it calls `search.get` on a string.
10. **app.overview.jsx:290. Recent activity dates omit the year.** The list is all-time (latest 5), so a date like "Aug 3" from 14 months ago reads as recent.

### 6. Schema, retention, privacy, observability, claims (unverified)
Marked **[branch]**: addressed by `fix/retention-privacy-review`, merged to main as PR #23 on 2026-10-09.
1. **Migration 20261008000000_us_coverage_flags re-enables coverage for every shop.** See Cross-cutting.
2. **claims.server.js:10. The Claims page doesn't check that the shop is installed.** readClaimsOverview checks only that the Shop row exists, not that it is INSTALLED, and calls Shopify before getShopConfiguration rejects. `ensureInstalledShop` exists for this. Still open on the branch.
3. **[branch] order-retention.server.js:60. The delivery sweep is one unbounded delete.** The final `webhookDelivery.deleteMany` has no shop or batch limit and no progress heartbeat, and there's no index on receivedAt, so it can hold locks past LOOP_STALE_MS. The branch batches it.
4. **order-retention.server.js:27. The purge deletes in-flight deliveries.** deleteOrderRecords removes all of an order's webhook deliveries, including PENDING and leased PROCESSING ones, which causes spurious "lease was lost" `webhook_processing_failed` alerts.
5. **order-retention.server.js:14. The purge deletes records needed for audit.** It permanently deletes confirmed purchases and refunds, claims in any status (including open SUBMITTED / REVIEW_REQUIRED) and ClaimEvent audit rows, with no exceptions. This conflicts with "preserve historical auditability", and billing-entry retention is still undecided.
6. **[branch] claims.server.js:11. Perf: sequential reads on the Claims page.** Its 3 independent reads run one after another, and the shop lookup is repeated.
7. **observability.server.js:5. Some event fields aren't scrubbed.** scrubEvent leaves `message`/`logentry`, `transaction` (which can be a raw URL path containing identifiers), `user` and `tags`. The branch now deletes `user` and allow-lists tags, but `transaction` and `message` still go through.
8. **[branch] observability.server.js:91. Caller fields can override Sentry tags.** Fields are spread into tags after `code` and `errorName`, so they can overwrite them, and numeric fields like durationMs become high-cardinality tags. The branch now uses a tag allow-list.

### 7. Scripts, ops, CI & E2E (unverified)
1. **shopify.app.staging.toml:45. The staging app config is missing settings.** It lacks the `shipping_protection_offer` metafield definition that the checkout extension requests, and `include_config_on_deploy = true`. Production, local and the .example file all have both. docs/production-readiness.md:819 says to confirm the definition exists on staging.
2. **operations-config.test.js:26. The config test checks the wrong staging file.** The metafield-contract test checks `shopify.app.staging.toml.example` instead of the tracked staging toml that is deployed, so it misses #1.
3. **e2e/support/merchant.js:404. The refund confirmation can be skipped.** `refundProtection` checks `confirm.isVisible()` right after clicking, without waiting, so a dialog that animates in late is missed and the refund is never submitted. The run then fails after 180s with a misleading error.
4. **e2e/restore.js:23. Restore depends on worker health.** It runs `database.preflight()`, which waits for the webhook queue to drain, before restoring the rate. With the staging worker down, restore never resets the rate and staging stays at 1% or 2%.
5. **e2e/auth.js:43. Paths with spaces break.** `new URL(...).pathname` is percent-encoded, so a path with a space writes to the wrong directory. Same in merchant.js:92 and auth-browser.js:60. Use `fileURLToPath`.
6. **ci.yml:43. CI runs each Postgres verifier twice.** `npm test` already runs them through postgres.integration.test.js, and the explicit verify:* steps run them again.
7. **verify-container.sh:47. Container verification uses different start commands from production.** It runs `node .../cli.js` and `node scripts/worker.js`, while production uses `npm run start` and `npm run worker`, so a broken npm script or a SIGTERM that npm doesn't forward isn't caught.
8. **e2e/support/database.js:23. The read-only-role check misses column grants.** The preflight checks only table-level privileges, so a column-level SELECT on `Session.accessToken` passes it.
9. **Dockerfile:9. The Docker build ignores the Node engine range.** .dockerignore excludes `.npmrc`, so `engine-strict=true` doesn't apply to `npm ci` in the image.
